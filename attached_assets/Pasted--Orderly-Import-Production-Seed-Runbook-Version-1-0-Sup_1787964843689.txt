## 2. Rules that govern everything

**Chronological order, one month at a time.** Approving a month changes the catalog the next month is classified against. Never load July before June is approved.

**Parse results freeze at upload.** After any parser change, re-upload the affected batch — re-reviewing is not enough. A batch staged before a fix keeps the old behaviour and will look correct while being wrong.

**Cross-vendor links before bulk actions.** The Category 2 bulk dialog flags likely duplicates but still includes them. Confirming overwrites saved `link_vendor_pack` decisions and recreates the duplicates.

**Verify against the server, not the UI.** The outstanding-decision counter lags, and rows keep their old status until re-render. After each step check `GET /api/inventory-import/orderly/batches/{id}/review-decisions`.

**Approve is irreversible.** Approved batches cannot be discarded. A database restore is the only recovery.

**Wipe scope:** changes to decision handling or review UI → re-run months that have decisions. Changes to parsing, geometry, identity keys or the approval write path → **re-run from May**.

**May has no decisions** — an empty catalog means nothing to compare against. The review machinery only engages from June.

### 3.3 Pre-bulk gate — MANDATORY, and the step most easily got wrong

**Do not confirm any bulk action before completing this.** The Category 2 bulk dialog flags *some* problem rows but not all, and confirming it sweeps in rows that should never have been offered.

Two classes are invisible to the dialog's warnings:

* **Unchanged rows.** Same vendor, same stable Item Code, same parsed pack as the prior approved month. These have nothing to decide and must not become variants. The dialog cannot flag them because the vendor has not changed.
* **Unflagged cross-vendor rows.** A genuine supplier change that the duplicate heuristic misses.

In the July run these two classes produced **12 identical-row forks and 5 missed cross-vendor links** — 17 wrong catalog items — because only flagged rows were checked.

**Procedure:**

1. Open **Create N new variants in bulk**, record every listed item and code, then **Keep reviewing** to close without confirming.
2. For every listed item, compare against the **immediately prior approved month** — not the union of all prior months:
   * **vendor + code + pack all unchanged** → must NOT be a variant. Do not include it. Report it — a row with unchanged stable evidence should not be offered as a new pack size at all.
   * **vendor differs from the prior month** → resolve as **"Keep one item, add this vendor pack"**, whether or not the dialog flagged it.
   * **same vendor, pack genuinely differs** → separate variant is correct.

   **Compare by product name and Item Code together, not code alone.** A cross-vendor switch brings a new Item Code, so a code-only comparison reports the row as a brand-new product and hides the switch.

   **Use the immediately prior month, not the union.** In the July run, `Apples - Red Delicious` appeared under Harvill's in May and Mr. Green's in June and July. Comparing July against May+June pooled together answered "vendor already seen" and misclassified it as a same-vendor pack change; it was actually the continuation of June's cross-vendor switch. That misclassification produced an approval-blocking identity error.
3. Resolve every cross-vendor row individually **before** returning to the bulk.
4. Re-open the bulk. It should now contain only same-vendor pack changes, with zero duplicate warnings.

This comparison is a workbook query, not manual inspection — group both months by Item Code and compare vendor and pack. For 30–100 items it takes seconds and is not judgment-dependent.

**Counts seen:** June 13 cross-vendor items / 41 rows; July 21 items / 60 rows, plus 17 rows that should have been excluded and were not.

**Check every page.** The list caps at 100 with no search. July's bucket held 160 rows across two pages; five flagged items sat on page 2.

### 3.4 Category 2 bulk

Re-open the bulk dialog. Duplicate warnings should now be **zero** (or only same-vendor cases you have verified). Confirm.

Verified in June: 32 items with 13 warnings → 19 items with 0 warnings after linking.

### 3.5 Category 1 bulk

Click **Link N compatible codes** and confirm the dialog header says *"Confirm N compatible code links."*

If it shows the *variants* dialog instead, a stale dialog is in the DOM — **reload the page** and retry. Decisions are already saved, so a reload is safe.

### 3.6 Remaining decisions

Work whatever is left individually. Expect:

- **Multi-location identity groups.** One product may appear as several groups — Shrimp 16-20 across 4, Lobster Claw 2, Demi-Glace 3. Resolve each, all targeting the same item.
- **Unknown-geometry rows** offer separate-variant only; linking is correctly blocked.
- **Held rows** offer fuzzy candidates — select on name, pack and location agreement.

### 3.7 Approve

1. Confirm the decisions banner is gone and Approve is enabled.
2. Confirm in writing that approval is intended for this batch.
3. Click once. **Wait 60–130 seconds without retrying.**
4. Record duration, resulting status, catalog counts.

If it fails: rollback is atomic and decisions survive. Read the error, fix the named row, retry once.

## 4. Production differences

**No reset.** Dev has been wiped repeatedly via Replit. Production has no in-app discard for approved batches and no agent to run database resets. **The first run must be right.**

**Backup with a tested restore, taken immediately before the seed.** It is the only recovery mechanism. An untested backup is not a safety net.

**Never send `force` on approval.** A `409 duplicate_date` is a stop sign. Forcing double-applies a month rather than replacing it.

**Approve under a named account.** That attribution is the only record of who committed an irreversible month.

**Use the same source files.** Archive and checksum the workbooks that produced a clean dev run; production uploads those exact bytes.

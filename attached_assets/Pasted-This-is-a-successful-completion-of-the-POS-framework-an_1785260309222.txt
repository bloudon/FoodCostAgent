## A few details worth documenting

### `released` connection behavior

Document exactly what remains after a connection is released:

* OAuth credentials revoked or removed
* Location mappings retained or archived
* Item mappings retained or archived
* Sync history retained
* Reconnection behavior
* Whether the partial unique index permits a new connection

The desired behavior is probably:

```text
released connection
→ no further synchronization
→ credentials unusable
→ history retained
→ mappings may be reused only when reconnecting the same provider/account
→ does not block a new provider connection
```

### Provider registry terminology

The recap says several providers are “manual-only, ready to be promoted.” That is good, but use capability data rather than one broad flag.

For example:

```typescript
availability: "connected" | "manual_only"

capabilities: {
  oauth: false,
  catalogRetrieval: false,
  salesRetrieval: false,
  locationMapping: false,
  itemMapping: false,
  backfill: false
}
```

That lets a future provider support file-based catalog retrieval or API sales retrieval without assuming every capability arrives at once.

### Setup-status ownership

Continue treating `GET /api/pos/setup-status` as the reusable truth for both Settings and future onboarding. Do not create separate onboarding completion flags later.

## Remaining Square pilot-readiness gate

The recap completes the framework, but it does not confirm several earlier Square-specific hardening items. Before connecting the first real restaurant, I would verify these explicitly:

1. **OAuth tokens are encrypted at rest** and never returned or logged.
2. **Reconnect Square** updates the existing connection and preserves mappings.
3. OAuth cancellation and callback failures show clear user-facing guidance.
4. The production callback URI works after VPS deployment.
5. Running the same sync twice does not duplicate sales or theoretical usage.
6. Refunds and modified prior-day orders update previously imported results correctly.
7. A manual sync cannot overlap a backfill or scheduled sync for the same connection.
8. Nightly timing works sensibly for the restaurant’s local timezone.
9. Token-refresh and revocation tests cover actual refresh failure, not only a pre-sync status check.
10. Square merchant identity is verified during reconnection so another Square account cannot silently replace the original one.

Some may already be implemented; they simply are not confirmed in this delivery summary.

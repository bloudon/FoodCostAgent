Yes — this is a meaningful finding, but **I would not let it expand #1178 into another big importer project.** The evidence actually gives us a pretty clean boundary.

## PM decision

**#1178 stays complete.** We add one **bounded source-shape amendment** for Progressive/the beer vendor:

> An invoice can reconcile even when product-line dollars do not equal the invoice header total, provided the difference is deterministically explained as a vendor-specific keg-deposit flow.

Then **#1182 owns the actual deposit balance/ledger behavior.**

The key architecture distinction is:

**Invoice importer:** “What happened on this invoice?”
**Deposit ledger:** “What is the running refundable deposit balance with this vendor?”

Those should not become the same subsystem.

### 1. Deposit inference: approve, but fail closed

The evidence is unusually strong:

* 25/25 product-line sums exactly equal Beer Expense.
* 17/25 header differences are exact ±$50 multiples.
* no deposit line items exist at all.

So for this vendor, deriving the deposit movement from the unexplained header-vs-product gap is justified.

But I would **not** make a generic rule that “invoice gap = deposit.”

The contract should be:

> If a vendor has an explicitly configured keg-deposit rate and the invoice's otherwise-unexplained gap is an exact integer multiple of that rate, classify the gap as **explained deposit flow**.

Otherwise it remains a reconciliation warning.

That protects us later when another vendor has freight, tax, fuel surcharge, credits, etc.

### 2. Do not hard-code `$50`

Even though Progressive is clearly behaving at $50, make this a **vendor-specific rate**, not a magic constant.

And I would make the rate effective-dated from the start, but very simply:

```text
vendor
deposit amount per keg
effective from
effective to (nullable)
```

Why? If Progressive goes to $60 next year, we shouldn't reinterpret old invoices.

No complex pricing engine. Just don't trap ourselves with a global `$50`.

### 3. Signed deposit event, not fake invoice lines

Do **not** synthesize fake “KEG DEPOSIT” product lines to make invoice arithmetic balance.

Preserve the source truth:

```text
Product lines: $X
Invoice header: $Y
Derived deposit flow: +/- $Z
Reconciliation: EXPLAINED
```

Then #1182 can create a deposit-ledger event linked back to that invoice.

That keeps beer pricing clean, exactly as the rehearsal demonstrated.

I would also preserve the source calculation/evidence so we can always show why FnB inferred the event:

> header amount − qualifying product/accounting amount = deposit flow

### 4. We need to prove the sign semantics once

Before writing balances, have Replit state from actual Progressive examples:

* Does **+$50** mean one new keg deposit charged?
* Does **−$50** mean one keg returned/refunded?

That is very likely, but it needs to be source-proven rather than inferred from arithmetic alone.

Once proven, that's the contract.

### 5. The duplicate invoice finding is separate and important

This is actually the more dangerous #1178 implication.

We previously strengthened identity to:

> vendor + invoice number

Progressive proves that may still be insufficient if the source genuinely contains **two distinct invoices with the same vendor invoice number**.

We should **not weaken dedupe globally by simply allowing duplicates**.

Instead, determine what distinguishes those two source invoices in the export. Preferred stable source identity should include the smallest real discriminator available, for example a source invoice ID if the export provides one.

If it does **not**, then return the exact distinguishing source fields before changing identity. Date + amount + invoice number might be usable evidence, but I don't want to canonize a fabricated composite until we see what the source actually gives us.

### 6. Sheet-name variation: make the parser tolerant, not vendor-specific

This:

> `Invoice Totals (Deposit Ledger)`

should not require Progressive-specific parser code.

Simple rule:

> Accept the canonical `Invoice Totals` sheet or an unambiguous sheet whose name begins with `Invoice Totals`.

Still fail if two candidate sheets exist.

That's small and sensible.

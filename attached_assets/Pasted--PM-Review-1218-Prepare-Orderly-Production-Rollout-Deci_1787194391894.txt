## Important clarification — Preflight vs Production Preview

Keep these as separate stages.

### Production preflight

The preflight may verify:

- deployed build identity
- database identity
- company/store scope
- required schema and constraints
- manifest/source evidence identity
- raw-source hash
- canonical source fingerprint
- existing mapping table integrity
- duplicate reliable vendor-product identities
- duplicate ORDERLY property + packSize.id mappings
- orphan mappings
- catalog counts
- whether prerequisites for the real production preview are satisfied
- zero-write catalog fingerprint before/after

It may also report high-level readiness expectations.

### Production preview

The production preview is a later, separately executed read-only step against the actual VPS production database.

That later preview is what should produce the authoritative production classifications:

- CREATE_VENDOR_ITEM_AND_MAPPING
- CREATE_MAPPING_ONLY
- ALREADY_SATISFIED
- DRIFTED_HOLD

Do not present a #1218 preflight projection as if it were the actual production preview.

## Required production evidence contract

The runbook/preflight must bind to:

- source system: ORDERLY
- property: `24472`
- exact approved manifest ID/hash
- raw source-file SHA
- canonical logical source fingerprint
- approved company identity
- approved store identity
- exact deployed build/version
- exact database identity
- required schema/migration state

Any mismatch must STOP.

No "close enough" or fallback behavior.

## Build identity

Do not rely only on package version numbers.

The runbook must define one reproducible build identity, preferably:

- git commit SHA / deployment commit
- migration/schema version
- application build identifier

The operator must be able to prove the VPS is running the reviewed code before production preview or APPLY.

## Database identity

Preflight must prevent accidental execution against:

- DEV
- staging
- another customer/company database
- another Bay Hill store/company scope
- an unexpected DB host/name

Return sanitized database identity evidence sufficient for the operator and PM to verify the target without exposing credentials.

## Recovery point

Define:

- backup command

- optional restore validation/check command if practical
- exact point in the runbook where the backup becomes mandatory

## Writer quiescence

Before production mutation, define how the operator ensures no competing writer can modify the affected catalog/mapping state during the bounded APPLY.

Prefer the smallest practical quiescence window.

Do not design broad downtime if a narrower write lock/maintenance window is sufficient.

#986 - Consolidate Mobile Foundation Safely

## What & Why

Resume the mobile consolidation as one Significant effort, using the historical hybrid Expo client as the approved functional base and selectively incorporating proven #981 count workflows.

The purpose is to establish one authoritative mobile client without breaking:

- authentication
- tenant/company/store scoping
- count mutations
- scan review
- catch weight
- voice waste
- embedded pages
- localization
- shared mobile/web contracts

This is a Significant task and must follow the project operating model:

PM decision → Builder → separate Reviewer → separate QA → task report → external review

If reviewer/QA separation cannot be verified, report:

`PROCEDURAL REVIEW — INDEPENDENCE UNVERIFIED`

Do not silently simulate independent review inside one continuous agent session.

---

# Approved Product Owner / PM Decisions

Record these decisions in `replit.md` before affected implementation begins.

Use a short dated architecture-decision entry with status:

`Approved`

## 1. Authoritative mobile client

The pre-existing historical hybrid Expo application is the consolidation and migration base.

Task #981 is not a second long-term mobile architecture.

Reuse selected #981 capabilities only when they:

- improve the consolidated client
- conform to approved contracts
- do not introduce a second auth/API/bridge/mutation dialect

Likely reusable #981 capabilities include:

- assigned-store count start
- session browsing
- manual line editing
- reviewed scan matching

These must be normalized against the historical contracts before adoption.

## 2. Floor Mode

Keep the separate Floor Mode product outside #986.

Do not:

- merge Floor Mode into the FnB Cost Pro mobile shell
- create role-based Floor Mode behavior
- replace Floor Mode
- infer its future product relationship

Its long-term relationship to FnB Cost Pro mobile remains a separate product decision.

## 3. Embedded authentication target

Target architecture:

- long-lived native authentication token remains in SecureStore
- embedded WebViews use the existing short-lived web-session token
- the long-lived login token should not remain the target mechanism for WebView URL authentication

However:

Do not implement this change unless the existing production API/web contract is verified from actual code and current behavior.

If the contract cannot be verified safely:

- preserve the current mobileToken bridge
- do not invent a replacement
- document the blocker
- create a follow-up decision/task

## 4. Native vs embedded ownership during consolidation

Native ownership:

- authentication
- navigation
- inventory session/count workflow
- camera/scanning
- catch weight
- voice capture

Embedded ownership during this transition:

- recipes
- vendors
- reports
- billing
- complex settings
- waste resolution/submission

Do not rebuild unrelated embedded management workflows in #986.

# Embedded-token verification requirement

“Verify the existing production API/web contract” must be evidence-based.

Before changing WebView authentication, the Builder must identify and record:

1. The exact backend route that issues the short-lived web-session token.
2. The middleware or route logic that accepts and validates it.
3. Exact file paths and relevant function names.
4. Token lifetime.
5. Token scope.
6. How the embedded WebView receives the token.
7. How the embedded page consumes/authenticates with it.
8. Whether it works with the current embedded-route/auth context.
9. Any dependency on the production web application that cannot be verified in this repository.

Documentation comments alone are not sufficient proof.

If any essential part of this flow cannot be verified:

- do not modify the authentication protocol
- preserve the current bridge
- record the missing evidence/dependency in the task report

# Implementation direction

## Establish one client foundation

Use the historical hybrid shell as the base.

Retain its proven:

- native capture flows
- SecureStore/auth model
- WebView integration
- i18n
- branding/assets
- voice bridge
- embedded-route handling

Selectively migrate #981 improvements only where they fit the approved target architecture.

## Authentication and API transport

End with:

- one auth provider
- one SecureStore strategy
- one token getter
- one authenticated API client strategy
- one WebView authentication bridge

Do not maintain competing auth hooks or API layers long-term.

Do not change production auth contracts without the verification requirement above.

## Count workflows

Integrate proven #981 count capabilities without creating a second mutation dialect.

Preserve:

- review-before-apply behavior
- atomic addQty semantics
- permission enforcement
- assigned-store restrictions
- session resume behavior

Do not revive obsolete legacy native count behavior merely because it exists historically.

# Stop conditions

Stop and request Product Owner / PM input instead of guessing if:

- the short-lived web-session token contract cannot be verified
- company/store scoping differs materially between implementations
- adopting #981 requires changing a shared contract
- voice bridge v1 is incompatible with the consolidated client
- addQty semantics differ
- production web changes appear necessary
- Floor Mode becomes a dependency
- the historical app and #981 disagree on a product behavior not already decided

Do not resolve these by inference.

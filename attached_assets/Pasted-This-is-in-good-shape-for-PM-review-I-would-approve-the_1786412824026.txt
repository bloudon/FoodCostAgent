The most important thing is that the work now appears to enforce the right invariant at multiple layers, not just in the UI:

> **Authentication may establish identity; invitations and approvals may grant access; neither may silently change the tenant ownership of an already-established user.**

That is the correct permanent rule for FnB.

A few parts of this batch are especially important. `8956991b` is more meaningful than it may look because the already-assigned-user conflict is now backed by a real-database integration test rather than only front-end or mocked behavior. `d1b210bc` and `c2ff80ed` together address both the action side and information-disclosure side of company-admin tenant isolation. ### One thing I would strengthen before closure

The **concurrent approval test** should verify database behavior, not just two API requests producing the expected UI result.

The acceptance criterion should be something like:

> Two administrators attempting to assign the same pending user concurrently must result in exactly one successful assignment. The losing operation must receive a controlled conflict response, and the final user/company/store state must reflect only the winning transaction.

That guards against a classic check-then-write race:

```text
Request A: user is unassigned ✓
Request B: user is unassigned ✓
Request A: assign company X
Request B: assign company Y
```

The existing 409 check is excellent, but we want proof that the database/update semantics make that race impossible rather than merely unlikely.

### Notification coverage deserves similar precision

For `7298862b`, I would define "exactly once" carefully. We don't necessarily need a sophisticated message queue/idempotency platform for MVP, but regression coverage should at minimum establish:

* only admins for the intended company are recipients;
* unrelated-company admins never receive it;
* retrying or revisiting the callback doesn't create obvious duplicate notifications;
* notification failure does **not** roll back or corrupt the user's authentication/invitation state.

Email is a side effect. It should never become authoritative to account assignment.

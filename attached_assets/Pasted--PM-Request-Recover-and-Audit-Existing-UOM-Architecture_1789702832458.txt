# PM Request — Recover and Audit Existing UOM Architecture System-Wide

## Objective

We previously invested substantial effort reviewing and designing FnB Cost Pro's unit-of-measure system, including purchasing, pack conversions, physical inventory counting, recipe costing, and inventory valuation.

Recent August counting problems suggest that parts of the established design are disconnected or inconsistently implemented.

**Before proposing any further UOM changes, recover the original design decisions and audit the current implementation against them.**

This is an investigation and documentation request only. No feature development or database changes are authorized.

## 1. Recover the original UOM design

Review `replit.md`, the PM decision log, completed development tasks, architecture documentation, and relevant source-code history.

Identify the original decisions governing:

* Canonical inventory units and their purpose.
* Vendor purchase units and pack geometry.
* Physical inventory counting units.
* Item-specific unit conversions.
* Recipe units and recipe costing.
* Issue/transfer units.
* Receiving quantities and conversions.
* Inventory valuation, weighted average cost, and price history.

Distinguish original approved decisions from later implementation changes or assumptions.

Provide task numbers, relevant commits, and source-file references wherever available.

**Do not reinterpret the intended design based solely on how the current code happens to behave.**

## 2. Document the intended end-to-end UOM model

Explain how an item moves through the complete system:

Vendor catalog → Purchasing → Receiving → Inventory → Physical counting → Recipe usage → Costing.

Use actual examples from Bay Hill inventory, including:

**Liquor example**

* Purchased by case or bottle.
* Physically counted as cases, bottles, and partial bottles.
* Converted internally to the canonical measurement quantity.
* Used in recipes by ounces or milliliters.
* Valued correctly regardless of the unit used during counting or purchasing.

**Food example**

Demonstrate an item purchased by case, counted by its practical physical packaging, and consumed in recipes by weight, volume, or portion.

Show where each conversion is defined, which system component owns it, and whether it is item-specific or generic.

## 3. Establish the physical counting contract

Our clarified product requirement is:

**Recipe measurement units must never become inventory counting units merely because they are the item's canonical or recipe unit.**

For liquor, an employee counts bottles and partial bottles—not mL or fluid ounces.

For other products, counting must use the item's appropriate physical or operational counting units.

Determine how our original design intended to support this distinction.

Specifically investigate:

* How count units were originally defined or derived.
* How cases, containers, individual packages, and partial packages are represented.
* Whether an item can have more than one valid physical counting configuration.
* How item-level count geometry relates to vendor-specific pack geometry.
* How fractional packages are converted and stored.
* Whether any existing count-unit configuration or conversion definitions are currently unused.

Do not assume we need a new Count Unit table or another UOM framework.

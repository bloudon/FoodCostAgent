# Bay Hill Orderly Extraction Path Reconnaissance — Deliverable

## 1. Executive Findings

- The backend lives entirely at `app.bepbackoffice.com/data/restaurantv2/...` — a clean, discoverable JSON REST API (not a black-box SPA).
- **Ingredient master and vendor-product relationships are the same endpoint and the same payload**: `GET /data/restaurantv2/spec/allSpecsForRestaurant/{restaurantId}` returns 3,739 records for Bay Hill (restaurant ID 24472), each an ingredient/"spec" with a nested `packSizes[]` array — this nested array **is** the vendor-product relationship data (vendor ID, vendor name, SKU, pack size, price, active flag) in the same call. No separate vendor-product endpoint exists or is needed.
- **Invoice headers and invoice line items are also the same endpoint**: `GET /data/restaurantv2/invoice/forRest/{restaurantId}?startDate=...&endDate=...` returns invoice headers with a nested `items[]` array (the line items) in one payload. A second endpoint, `GET /data/restaurantv2/invoice/explain/{internalInvoiceId}`, returns the identical structure for a single invoice (used for on-demand detail views).
- **Confirmed, evidence-based answer to the flagged "especially important" question**: invoice line items carry a `packSize.id` foreign key (e.g., 2905156) that **does** match cleanly against `allSpecsForRestaurant`'s nested `packSizes[].id` for the correct spec/vendor-product. However, the invoice line's own embedded `packSize` sub-object is **not** hydrated with the enrichment fields (description, supplier name, itemCode, etc. all come back null/0 inside that sub-object) — the join must be done by ID against the separate ingredient-master payload, not read directly off the invoice line.
- GL/accounting category data is fully resolved and nested per line item (`category.accountNumber`, `accountName`, `accountType`, `accountSubType`, plus a nested `incomeAccount` for the revenue side) — this is real structured GL mapping, richer than what's visible in the basic UI list views.
- The UI's "Restaurant Ingredient" column (matched ingredient name per invoice line) is **not** a field returned by the invoice endpoint — it must be a client-side join, not a server-provided value.
- `invoiceStatus` shows `"ReadyForReview"` on both a today's invoice and a **July 2024** invoice — this field appears static/unused for Bay Hill rather than reflecting actual review completion, consistent with Approved/Paid/Exported all showing false across the board in the UI.
- Client-side filtering confirmed: ingredient search, invoice date-range changes, and vendor filters in the UI trigger **zero new network calls** — Angular fetches these bulk payloads once and filters everything in-browser afterward.

## 2. Ingredient Master Endpoint Map

- **Endpoint**: `GET /data/restaurantv2/spec/allSpecsForRestaurant/24472`
- **Method**: GET, no body, restaurant ID in path, no pagination params — returns the full set in one call (3,739 records).
- **Response**: flat array. Each record: `id` / `specId` (stable, restaurant-scoped ingredient ID), `name`, `packSizes[]` (nested vendor-products).
- There is also a **separate global reference catalog**, `GET /data/restaurantv2/orderlySpec/` (12,204 records, fields: `id, name, uom, categoryName, isGraphable, defaultPrice, parentId, hasEnoughData, hasPicture, isSelectable, categoryId`) — this is Orderly's platform-wide taxonomy, not Bay Hill-specific data, and uses a **separate ID space** from the restaurant-scoped spec IDs (e.g., global "Butter - Unsalted" = id 5342; Bay Hill's actual instance ids are in the millions, e.g., 6297822).
- GL code, category, storage location, active/inactive, and price-history detail were **not** fully visible in the truncated ingredient-level object — only the nested vendor-product (`packSizes`) records showed price/active/GL-adjacent fields directly. The ingredient-level GL/category association is confirmed instead on the invoice-line side (`category.accountNumber`).

## 3. Vendor-Product Endpoint Map

- **No separate endpoint** — vendor-product data is the `packSizes[]` array nested inside each `allSpecsForRestaurant` record.
- **Fields per vendor-product** (`packSizes[]` entry): `id` / `packSizeId` (stable vendor-product ID), `productId` (a second, distinct product-level ID), `packSizeDesc`, `itemDesc`, `description`, `size`, `uom`, `pack`, `supplierId` (stable numeric vendor ID — e.g., 40 = Sysco, 6510 = Mr. Green's Produce), `supplierName`, `brand`, `itemCode` (vendor SKU), `isActive`, `price`, `globalRegion`.
- Confirmed: multiple SKUs from the same vendor, and alternate vendors for the same ingredient, are both represented as **separate entries in the same `packSizes[]` array** — no separate alternate-vendor structure exists; it's all one flat list per spec.
- `price` was `null` in the sample records inspected — current/latest price for a given vendor-product may live elsewhere (possibly resolved via the most-recent invoice line for that packSize ID, client-side) rather than being stored directly on the spec record. This is a genuine unknown, not confirmed either way.
- No EDI/OCR/manual source flag found on the vendor-product record itself — that flag (`invoiceIsEDI`) lives on the **invoice line**, not the vendor-product/catalog record.

## 4. Invoice Header Endpoint Map

- **Bulk list endpoint**: `GET /data/restaurantv2/invoice/forRest/24472?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD` — **requires** both date params (confirmed via a 400 error when omitted). Returns `{invoices: [...], uniqPackSizes: [...], uniqCategories: [...]}`.
- **Single-invoice endpoint**: `GET /data/restaurantv2/invoice/explain/{internalInvoiceId}` — same schema, one invoice, used for on-demand detail views (fired when opening a specific invoice from certain screens).
- **Header fields**: `id` (stable internal invoice ID, distinct from the vendor's own invoice number), `invoiceNumber`, `restaurantId`, `restaurantName`, `supplierId`, `supplierName`, `createdTimestamp`, `deliveryDate`, `paymentDueDate`, `paymentApprovalStatus`, `paymentApprovalLevel`, `paymentStatus`, `total`, `taxCharge`, `kegCreditCharge`, `kegDepositCharge`, `deliveryCharge`, `otherCharge`, `documentId`, `invoiceStatus`, `items[]`.
- No explicit credit/negative-invoice flag field was inspected directly, but the earlier UI observation (negative `$` totals with a "-CR" suffix in the invoice number) is consistent with credits sharing the exact same schema as regular invoices — just a negative `total`.
- No pagination parameters found or needed within a given date range; the client appears to call this once per relevant range and cache the result.

## 5. Invoice Line-Item Endpoint Map

- **No separate endpoint** — line items are the `items[]` array nested inside each invoice header record (from either endpoint above).
- **Line-item fields**: `id` (stable line ID), `total`, `deliveryDate`, `supplierName`, `supplierId`, `restaurantName`, `restaurantId`, `invoiceId` (parent FK), `attachmentUrls[]`, `useTaxApplies`, `itemCode` (vendor SKU, populated directly on the line), `pack`, `size`, `uom`, `isCatchWeight`, `quantity`, `description` (was `null` in samples), `packSize` (nested object — see below), `invoiceIsEDI` (boolean, confirmed source-type flag), `invoiceIsFromDataManager` (boolean, likely marks manual/OCR-management-tool entries), `category` (fully resolved GL account object), `catchWeightUomOverride`.
- The nested `packSize` object on the line item carries only an `id` reliably — its other fields (`itemCode`, `description`, `supplierName`, etc.) came back null/zero in every sample checked, **even on a 2-year-old invoice**, suggesting this is a consistent pattern rather than a review-status artifact.
- **Confirmed by direct cross-reference**: that `packSize.id` value does successfully match an entry in the `allSpecsForRestaurant` payload's `packSizes[]` array (verified: invoice line itemCode "7037374" / packSize.id 2905156 matched exactly to spec "Water Logo" / specId 6301205 in the ingredient master).

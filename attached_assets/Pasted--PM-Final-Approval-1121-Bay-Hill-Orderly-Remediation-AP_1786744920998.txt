## PM Final Approval — #1121 Bay Hill Orderly Remediation

APPROVED TO BUILD — Significant / Production-Write-Capable.

The task direction is correct. Add the following constraints before implementation.

### 1. Production execution must be a separate explicit step

Building and testing #1121 does NOT authorize an automatic production apply.

Sequence must be:

1. build tool
2. DB-backed tests
3. Reviewer
4. QA
5. run REPORT MODE against production
6. return the production report to PM/Product Owner
7. obtain explicit approval of the exact SAFE_CANDIDATE group manifest
8. only then run APPLY MODE against production
9. run post-apply reconciliation

No production mutation may occur during development, test, review, QA, or initial production discovery.

There must be no code path that converts a report run into an apply run implicitly.

---

### 2. Canonical-item selection must be deterministic and reported

For every SAFE_CANDIDATE, the tool must explain why one inventoryItemId is proposed as canonical.

Use evidence such as:

- existing authoritative external mapping
- earliest valid import-created identity
- downstream references
- metadata completeness
- store/location linkage
- existing historical use

Do not select:

- lowest UUID/string order
- first query result
- display-name preference
- arbitrary row order

If more than one candidate remains equally valid, classify:

`AMBIGUOUS`

Do not manufacture a winner.

The report must include:

- proposedCanonicalItemId
- canonicalSelectionReason
- alternativeCandidateIds

---

### 3. Count-history evidence should normally be repointed, not rewritten

The core remediation concept is:

> multiple accidental inventory identities become one canonical identity

It is NOT:

> rebuild May/June inventory history.

Preserve:

- source quantities
- source row provenance
- physical locations
- count dates
- source workbook/batch identity

Where historical count rows reference a duplicate inventoryItemId, repoint that FK to the canonical item only if the schema allows this without altering the original source/count facts.

Do not recalculate or replace historical quantities during remediation.

If a uniqueness constraint prevents several legitimate location/count rows from pointing to the same canonical item, STOP that group and report the exact constraint/evidence instead of deleting or aggregating rows to make the merge succeed.

---

### 4. Valuation reconciliation needs two levels

Post-apply reconciliation must prove both:

#### Period-level

May 2026 expected applied valuation:
`$254,286.67`

June 2026 expected applied valuation:
`$261,007.67`

The repaired data must reconcile to those existing applied baselines unless a discrepancy is explicitly explained and approved.

#### Group-level

For every repaired duplicate group, report:

- valuation contribution before
- valuation contribution after
- delta
- affected locations/count rows

Expected delta should normally be `$0.00`.

This lets us catch a case where the monthly grand total happens to remain correct while value moved incorrectly between items/locations.

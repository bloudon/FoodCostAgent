The vendor-product-centric resolution is the right correction. The workbook gives us Vendor context + Item Code + Pack Size, so resolving the purchasing identity first and then following that to the inventory item is cleaner than trying to match directly against inventory names.

There are **four things I would change**.

First, the opening premise still says:

> “keeps nothing about the invoice itself (no invoice or line tables)”

We should not let that become a design assumption until Replit checks the current repo. We already did historical invoice work earlier. Change that sentence to something neutral like:

> “The current photo-invoice workflow is optimized for single-invoice price capture and does not currently provide the staged bulk historical-import workflow needed here.”

That avoids accidentally authorizing duplicate invoice infrastructure.

Second, I would remove **“new tables”** from Done Looks Like:

> “Approval persists invoice headers and line items durably (new tables)”

should become:

> “Approval persists invoice headers and line items durably using the existing invoice domain where possible; add only the minimum schema required after repo audit.”

That is the biggest remaining architecture issue.

Third, tighten this sentence:

> “via existing ORDERLY external mappings / item code / name”

because name should not appear as if it is a peer identity mechanism. You already fixed this properly in Step 2. Make Done Looks Like agree with it:

> “via authoritative ORDERLY mappings and vendor-item identity, with description used only as supporting review evidence.”

Fourth, I would explicitly protect **historical price chronology**. Right now Step 4 says “record dated price observations,” but it does not yet say that importing old invoices cannot become the current price simply because they were imported later.

Add:

```md
Historical price observations must be ordered by their business-effective invoice date, not import/created timestamp. Importing a May invoice after an August price exists must never make the May price current solely because it was imported later.
```

## One identity nuance I want resolved

This line:

> item identity must flow through `inventory_item_external_mappings` … exactly as the inventory import does — the mapping row is the claim authority

is correct for the **canonical inventory identity**, but now that we have made the importer vendor-product-centric, I would distinguish the two identities:

```text
Source purchasing identity:
Vendor + property-scoped Orderly Item Code + Pack Size evidence
        ↓
Existing FnB vendor item / vendor-product relationship
        ↓
Authoritative ORDERLY external mapping
        ↓
Canonical inventory item
```

We don't want future code to interpret “mapping row is claim authority” as permission to skip validating that the **vendor SKU/pack we purchased** is the correct vendor product.

The mapping answers:

> Which canonical FnB inventory item does this Orderly source identity represent?

The vendor-item relationship answers:

> Which purchasable SKU/pack from this vendor was actually invoiced?

We need both.

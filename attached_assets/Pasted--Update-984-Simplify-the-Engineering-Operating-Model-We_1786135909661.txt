# Update #984 — Simplify the Engineering Operating Model

We are simplifying the operating model established by Task #984 before using it for Significant production work.

This is a process/documentation/configuration change only. Do not change product functionality.

## Goal

Replace the six-role / three-level operating model with the smallest structure that still protects FnB Cost Pro against:

- self-certifying work
- hallucinated architecture
- auth or tenant-scoping mistakes
- data-integrity errors
- costing/calculation errors
- shared-contract drift
- regressions

Use this principle:

> One builder. One checker. One short report. Escalate only when risk justifies it.

## Final operating model

### External roles

- Product Owner — final business/product decision
- Primary PM / Architect — defines significant product/architecture direction and reviews shipped work
- Independent Challenger — second opinion on Significant work
- Replit — engineering implementation and technical review

Do not create additional permanent organizational layers.

### Replit roles

Use only three operational roles:

#### Builder
Implements the approved task.

#### Reviewer
Checks architecture, security, authorization, tenant isolation, shared contracts, data integrity, costing/valuation logic, inventory mutation semantics, and implementation deviations.

Reviewer may BLOCK work.

Reviewer may recommend an architecture change but may not approve or invent new product architecture.

#### QA
Checks acceptance behavior, regressions, edge cases, and test evidence.

QA may not waive a Reviewer block.

### Independent review rule

For Significant work:

- Builder may not certify its own Reviewer or QA result.
- Reviewer and QA should run in fresh, separately instantiated agent workstreams/sessions when the platform supports this.
- If Replit cannot create that separation automatically, stop after the Builder phase and tell the Product Owner exactly which fresh session must be started next.
- Do not silently simulate independence by relabeling one continuous agent session.
- If separation cannot be verified, report:
  `PROCEDURAL REVIEW — INDEPENDENCE UNVERIFIED`

## Task classification

Use only two classes.

### Routine

Examples:
- copy changes
- styling
- isolated visual fixes
- low-risk refactors with no behavioral impact

Flow:
Build → Test → Done

### Significant

Any work that can affect:

- user workflow or behavior
- stored data
- API behavior or contracts
- authentication
- authorization or permissions
- tenant/company/store scoping
- calculations or costing
- inventory mutations
- schema or migrations
- mobile architecture
- shared contracts
- vendor integrations
- AI interpretation contracts
- destructive changes
- another feature's behavior

Flow:
PM decision → Build → separate Reviewer → separate QA → task report → external review

Rule:
If uncertain, classify the task as Significant.

## Always-active guardrails

Preserve these concrete project protections.

- Never commit or expose secrets.
- Never bypass tenant/company/store scoping.
- Never silently change authentication contracts.
- Never silently change approved shared contracts.
- Preserve the established mobileToken/WebView bridge unless an approved decision changes it.
- Preserve the embedded-route whitelist contract unless an approved decision changes it.
- Preserve waste voice bridge v1 unless an approved decision changes it.
- Preserve approved inventory mutation semantics.
- Preserve unit/pack normalization rules.
- Treat costing, valuation, theoretical cost, variance, and purchasing calculations as high-risk data-integrity logic.
- Preserve existing working behavior unless replacement is explicitly in scope.
- Document material deviations from the approved task.

This is a strong plan and the two-task split is correct. I would approve it **after tightening a few backend rules** so the new fields actually control behavior instead of becoming another layer of descriptive metadata.

The main gap is that `primary_sales_method` is currently being added and displayed, but the plan does not yet say what it changes operationally.

## Required adjustments to #612

### 1. Enforce valid provider/method combinations server-side

The UI should not be the only thing preventing this:

```text
Provider: HungerRush
Primary method: pos_connector
```

The company PATCH handler should enforce:

```text
posProvider = null
→ primarySalesMethod must be null

primarySalesMethod = pos_connector
→ selected provider must exist in the registry
→ provider must support salesRetrieval
→ provider must have a registered connector adapter

primarySalesMethod = manual_upload
→ allowed for any recognized provider, including other
```

Return a structured `422` response for invalid combinations.

### 2. Make the primary method operational

Define what it actually controls:

```text
primary_sales_method = pos_connector
→ scheduled POS synchronization is enabled

primary_sales_method = manual_upload
→ scheduled POS synchronization is disabled
→ existing connection and mappings may remain retained
→ manual upload remains the primary source
```

`runAllIncrementalSyncs()` should only include companies where:

```text
primary_sales_method = pos_connector
```

and the connection provider matches the company’s selected `posProvider`.

Otherwise, a company could select manual upload while Square continues importing sales every night.

### 3. Enforce one usable POS connection per company

The MVP assumption is one provider and one primary connection per company. The backend should enforce that.

At minimum:

* Do not permit two active POS connections for the same company.
* OAuth callback must not create a duplicate Square connection.
* Reauthorization updates the existing connection.
* `setup-status` must never arbitrarily select one of several records.

A service-level guard is required. A database constraint or partial unique index would be even safer if it fits the current status model.

### 4. Tighten the provider-change guard

“Active connection” needs a precise definition.

A Square connection that has a revoked token and status `disconnected` is still a retained configured connection. Allowing the provider to change at that point could orphan its mappings.

Block provider changes while any connection exists that has not been **explicitly disconnected, archived, or removed by the user**.

Distinguish:

```text
Disconnected because credentials failed
```

from:

```text
Intentionally disconnected and released for provider change
```

Those are different lifecycle states.

### 5. Define setup-status counts precisely

`itemsMapped N/total` can become misleading unless the denominator and ignored records are defined.

I recommend returning:

```typescript
interface PosSetupStatus {
  providerSelected: boolean;
  primaryMethodSelected: boolean;
  connectorAvailable: boolean;

  connectionStatus:
    | "not_configured"
    | "not_connected"
    | "connected"
    | "disconnected"
    | "error";

  locations: {
    total: number;
    mapped: number;
    ignored: number;
    unresolved: number;
  };

  items: {
    total: number;
    mapped: number;
    ignored: number;
    unresolved: number;
  };

  lastSuccessfulSyncAt: string | null;
  lastAttemptedSyncAt: string | null;
  latestSyncStatus: string | null;
  warningCount: number;
}
```

A deliberately ignored POS item should count as **resolved**, but not as mapped:

```text
resolved = mapped + ignored
```

Do not merge ignored, skipped and unresolved into one ambiguous count.

### 6. Use a constrained database value

Rather than an unrestricted text field, use either:

* A Postgres enum, consistent with the current schema conventions, or
* A `CHECK` constraint permitting only `pos_connector`, `manual_upload`, or `NULL`.

Application validation alone is not enough for a field that controls scheduled ingestion.

## Registry refinement

The registry design is right. One small distinction:

```typescript
getConnector(providerKey)
```

should throw or return a typed result such as:

```text
unknown_provider
connector_unavailable
connector_available
```

Toast and HungerRush may appear in public provider metadata but have no adapter. They should not look like registry lookup failures.

Conceptually:

```typescript
interface PosProviderDefinition {
  providerKey: string;
  displayName: string;
  availability: "available" | "manual_only" | "coming_later";
  capabilities: PosCapabilities;
  connector?: PosConnector;
}
```

The public metadata excludes `connector`, while the server can still distinguish a recognized manual-only provider from an invalid key.

For existing Square-specific OAuth routes, it is acceptable to preserve the current URLs. Internally, however, connection-based sync and mapping operations should resolve the adapter from the connection/provider record rather than repeatedly calling:

```typescript
getConnector("square")
```

Square-specific connect and callback routes can remain compatibility endpoints for now.

## Adjustments to #613

The UI plan is well scoped. I would add four rules.

### Save configuration before beginning OAuth

When the user chooses:

```text
Provider: Square
Method: Connected POS
```

save those settings successfully before opening Square OAuth.

The OAuth initiation endpoint should then verify:

* Company provider is `square`
* Primary method is `pos_connector`
* Square is available in the registry
* No conflicting provider connection exists

Do not rely only on the button being hidden or shown correctly.

### Save provider and method atomically

Do not make two independent requests that temporarily leave the company in an invalid combination.

Use one PATCH payload:

```json
{
  "posProvider": "square",
  "primarySalesMethod": "pos_connector"
}
```

and validate the complete intended state server-side.

### Explain what changing the method does

When changing from Connected POS to Manual Report Upload:

```text
Automatic Square synchronization will stop.
Your Square connection, mappings and previous sales will be retained.
You can switch back to Connected POS later.
```

This is different from changing the provider, which should require explicit disconnection first.

### Show merchant identity, not only merchant ID

The user-facing card should preferably display:

```text
Square account: Brian's Pizza
Merchant ID: ABC123...
```

The raw merchant ID is useful for support, but it should not be the primary identity shown to restaurant managers.

### Reconciling against Orderly's displayed totals

Orderly's UI shows $254,285.74 / $261,006.73 / $254,298.83 — roughly $0.93 lower each month. This is explained and expected: Orderly's Summary row carries full floating-point precision (`254285.737889`) which its UI rounds, while Detail rows are cent-rounded. Summing ~5,400 cent-rounded rows produces ~$0.93 of upward bias.

**FnB matches the Detail rows — the auditable source.** Always reconcile against the Detail sum, not the displayed total.

## 2. Known state — items to review, not blockers

### 2.1 Four suspect forks in the June→July comparison

44 name-paired forks were reported. The large majority are **correct** — same-vendor pack changes deliberately kept separate (Casamigos minis vs bottles, Makers Mark, Crown Royal, Tito's, Creamers, Buttermilk, Egg Whites, Chives, Cumin).

**Four need confirmation:**

| Item | Prior vendor → July | Why it forked |
|---|---|---|
| Mizuna | Harvill's → Mr. Green's | unknown geometry, no link offered |
| Mushrooms - Blends/Mix | Mr. Green's → Fungi Jon | `1/1 Case`, unverifiable pack |
| Popcorn Kit | (blank) → Sysco | no prior vendor to compare |
| Potato Skins | GFs Store → Cheney Brothers | unknown geometry |

Each is a genuine cross-vendor switch where the vendor-pack link was unavailable. They may be true duplicates. Low value, but they should be classified before the register treats them as correct.

### 2.2 Cumulative data-quality figures

Across all three approved batches, not per month:

* 3,140 rows without a valid source code
* 3,140 rows without a vendor
* 461 rows with partial or unparseable pack geometry
* 2,637 rows with Orderly par targets

The first two are the same population — cellar wine and similar entered in Orderly without a code or supplier. Invoice import is the remedy.

### 2.3 Pack geometry gaps

~133 items remain with genuinely opaque `1/1 Case` geometry, ~$16.3k of inventory value. Value is unaffected; costing and unit conversion are. The **Hit List** ranks the 22 highest-value cases — six items (three Busy Bean products, three Font Group bars) account for $8.4k of the $16.3k.

## 3. Production readiness — what is still required

### 3.1 The operator path for July was never completed through the UI

This is the most important gap and should be closed before production.

July's approval **failed four times through the Approve button**. The successful commit came from Replit invoking the approval service directly in a diagnostic wrapper, after which the job record had to be repaired manually.

The seeded data is correct and verified. But the **process** — the thing production will repeat — has not been demonstrated end-to-end for July with the final code in place.

**Recommendation:** before production, wipe development and complete one clean May → June → July run entirely through the UI on the current build. That validates the final combination of fifteen fixes together, which has never been exercised as a whole. It also re-tests the four suspect forks under corrected classification.

### 3.2 Approval idempotency is unverified

Approvals run 60–130 seconds with limited progress feedback. On one occasion a 5,518-row approval took the development server down at 108 seconds.

**Approved batches cannot be discarded** (`POST /discard` returns 409). Idempotency has never been tested.

The operational rule is therefore: **never retry a slow approval.** That rule protects production, but confirming idempotency would be better than relying on discipline.

### 3.3 Production has no reset

Development was wiped six times during this work. Production has no in-app discard for approved batches and no equivalent reset path.

**Requirements before the first production import:**

* A verified database backup with a **tested restore** — the only recovery mechanism
* Approval performed under a **named account**; attribution is the sole record of who committed an irreversible month
* **Never send `force`** on approval — a `409 duplicate_date` is a stop sign, and forcing double-applies rather than replaces
* The **same source workbooks**, archived and checksummed

### 3.4 Known UI constraints the operator must work around

* The review list paginates at 100 **with no search**. July's bucket held 160 rows; five items sat on page 2 and were invisible to a page-1 scan.
* Cross-vendor links must be applied **before** the Category 2 bulk. Confirming the bulk first overwrites them.
* The bulk dialog's duplicate warning fires only on **cross-vendor** candidates. Every listed item must be checked against the prior month, not only the flagged ones — this caught 7 items in July that were never flagged.
* Compare against the **immediately prior approved month**, and by **product name and code together**. A cross-vendor switch brings a new Item Code, so code-only comparison hides it.
* The Inventory Items page renders **0 items** while the API returns thousands. No GUI catalog cleanup is available.

## 5. Recommendation

The financial objective is met: three months reconcile exactly, and the import is repeatable.

**The remaining risk is process, not data.** Fifteen fixes landed during this run, and the final combination has never been exercised end-to-end through the operator path. Production offers no second attempt.

One clean UI-driven run on development — perhaps two hours of review work — converts the current position from "the data is right" to "the process is proven." That is the difference worth buying before touching live club data.

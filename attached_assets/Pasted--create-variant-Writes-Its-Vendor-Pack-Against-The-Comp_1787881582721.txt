## Summary

A row with a saved `create_variant` decision fails approval with:

> **Approval failed** — Orderly row 1827 conflicts with the existing pack for this vendor and inventory item.

`create_variant` creates a **new** inventory item. A new item has no existing vendor pack, so there is nothing for the vendor pack write to collide with. The collision therefore indicates the vendor-pack write is targeting the **wrong item**.

## Likely cause

The saved decision carries the comparison target:

```json
{ "rowIndex": 1827,
  "decision": { "action": "create_variant",
                "comparableInventoryItemId": "c118ae82-0ce7-42c5-8f96-d3633d92e064" },
  "revision": 1 }
```

`comparableInventoryItemId` is the existing item the row was *compared against* — it is evidence, not a write target. If the mutation path uses it as the `inventoryItemId` for the vendor-pack upsert instead of the id of the newly created variant, the unique constraint on (vendor, inventory item) fires against the pre-existing pack and the transaction aborts.

This would explain why `create_variant` — the outcome specifically intended to avoid collisions — is the one failing.

You’re right. My previous framing incorrectly treated **“POS Provider”** as passive metadata and the Square connection as a separate concept.

Your intended model is cleaner:

> A company identifies its POS, chooses how sales data will enter FnB, and—when electronic connectivity is selected—the universal connector framework loads the appropriate provider adapter.

Square is simply the first implemented adapter within that framework.

## Correct product model

During company setup:

```text
Which POS do you use?
[ Square ▼ ]

How should FnB receive sales?
○ Electronic connection
○ Manual report upload
```

When **Electronic connection** is selected:

```text
Square connector available
[ Connect Square ]
```

When **Manual report upload** is selected:

```text
[ Configure sales report import ]
```

For a provider that does not yet have an electronic adapter:

```text
Electronic connection is not yet available for HungerRush.

[ Use manual report upload ]
[ Request this integration ]
```

The provider selection is therefore authoritative. The connection record is the implementation and current status of that choice.

```typescript
interface CompanySalesConfiguration {

  salesImportMethod: "electronic" | "manual";
```

The connector framework then resolves:

```typescript
connectorRegistry.get(company.posProviderKey)
```

Square would register as:

```typescript
{
  providerKey: "square",
  displayName: "Square",
  capabilities: {
    electronicSalesSync: true,
    catalogImport: true,
    locationMapping: true
  },
  adapter: squareConnector
}
```

The OAuth connection record is related operational state:

```text
Company POS: Square
Sales method: Electronic

```

Those are not three unrelated settings. They are one configuration with three layers:

1. **Provider:** Square
2. **Method:** Electronic
3. **Status:** Connected

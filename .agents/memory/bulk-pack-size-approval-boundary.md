---
name: Pack-size approval boundary
description: Rules for safely linking or creating Orderly pack-size variants from individual and bulk review actions.
---

Bulk selection is a convenience layer, not an authorization boundary. The server must independently allow a shared decision only when the complete reliable source-code group stays within one server-derived description-plus-pack identity. Verified incompatible packs may create separate variants. A single otherwise eligible possible-recode row with incomplete geometry may also create an explicit separate variant while remaining classified as unknown; it may never link to the candidate or claim normalized compatibility. Unknown geometry does not authorize bulk creation or relax conflicting, divergent, partial-group, unreliable-code, tenant, or revision guards.

**Why:** A client can submit a complete-looking group payload directly, bypassing even a deliberately strict bulk selector. Source-code membership alone does not prove product identity. Unknown geometry is not incompatibility, but reviewers still need a non-comparable outcome that preserves a stocked source row without falsely linking it.

**How to apply:** Under the batch lock, recompute preview evidence and candidate identity. Allow the unknown exception only for one explicit separate-variant decision on a single eligible reliable-code row. For bulk actions, recompute group membership and identity, reject missing/divergent keys, and require every source-code row to be eligible and resolve to one reviewed comparable item. Test draft-save and approval parity, link rejection, rollback, and UI wording.
